# Timer

There are three full-screen UIs a single task can open, all driving the same underlying `TaskLog` state machine (see [task-lists-api.md](../api/task-lists-api.md)):

- **`components/TaskFormScreen.tsx`** — the primary one today. Opened by tapping "Start Task" on a `form` task (the only creatable task type, see [task-lists.md](task-lists.md#task-types)); renders one control per `formFields` entry (number input or yes/no) instead of a ring, but tracks elapsed time the same wall-clock way described below and completes through the same `PATCH /api/task-logs`, just with a `formData` payload attached. Shows an "Instructions" button under the task title when the task has any, same as the list rows — see [task-instructions-employee-view.md](task-instructions-employee-view.md). Also embedded inside `TaskListSessionView.tsx`'s guided walkthrough for its "running" phase, so the button reaches the shift-window session flow too.
- **`components/TimerScreen.tsx`** — the ring-based countdown/stopwatch timer this doc mostly describes below. Only reachable for a `standard`/`stopwatch` task — the pre-pivot personal-habit types kept in the schema for compatibility but no longer creatable (see [task-lists.md](task-lists.md#task-types)) — so on current data this path is effectively legacy, exercised only by any old tasks that predate the pivot. Also shows the Instructions button (see [task-instructions-employee-view.md](task-instructions-employee-view.md)), for parity even though rarely hit.
- **`components/TaskListSessionView.tsx`** — a sequential, full-screen flow that steps through every task in a list one at a time, opened via "Start Tasks". Internally it renders `TaskFormScreen` for a `form` step and its own ring markup for a `standard`/`stopwatch` step — see "Form tasks inside a session" below.

All three are orchestrated by `components/TasksView.tsx` (or, for the session case, by `TaskListSessionView.tsx` itself once opened). The elapsed-time/wall-clock mechanics below apply to `TimerScreen` and `TaskListSessionView`'s own ring rendering; `TaskFormScreen` tracks elapsed time the same way (for the `actualMinutes` fallback) but has no ring/drag UI of its own.

## How elapsed time is computed

Neither timer counts `setInterval` ticks as the source of truth. Both use the same pattern: `baseElapsedRef` banks seconds accumulated before the current running segment, `runStartRef` holds `Date.now()` for when the current segment began (`null` if paused), and a `recompute()` function derives `elapsed = baseElapsedRef + (Date.now() - runStartRef)` from real timestamps. The `setInterval(recompute, 1000)` tick is purely cosmetic — even if it's throttled or suspended while the app is backgrounded, the next tick (or the resync below) recomputes the *true* elapsed time from wall-clock time, so no time is silently lost.

A separate effect listens for `visibilitychange`, `focus`, and `pageshow` and calls `recompute()` immediately on any of them, so the displayed time snaps to correct the instant the app returns to the foreground rather than waiting up to a second for the next tick.

Pause/Resume is purely local UI state (`isRunning`) — it makes no API call.

## Dragging the ring to set elapsed time

The whole icon/name/ring area of the running screen is a drag surface — not just the ring itself, which is too thin and small a target to grab reliably. Touch or click down anywhere in that area (excluding the top bar and the buttons below) and drag around in a circle like a rotary dial to set elapsed time directly, with a small handle dot always sitting at the current arc tip as a visual affordance for what you're winding. The wrapping `<div>` owns the gesture (`touch-action: none`, `select-none`, `pointer-events-none` on everything inside it) so the ring, icon, and text are purely decorative and never intercept the drag — this also avoids SVG's `pointer-events: stroke`, which has inconsistent browser support and was the original (buggy) approach.

One full clockwise lap adds one "revolution" of time: for a countdown task, that's `projectedMinutes` (so two laps sets 40 minutes over a 20-minute target); for a stopwatch task (no target), it's a fixed 30 minutes, matching the ring-fill soft cap that mode already uses visually. Dragging counter-clockwise back past the start clamps at 0 — it can't go negative. There's no upper clamp; winding multiple laps over target is the point, and the existing burgundy "over target" ring color/styling already covers that case.

The gesture logic lives in `lib/useRingDrag.ts` — a small hook, not a shared visual component, since `TimerScreen` and `TaskListSessionView` each render their own ring markup independently and only the pointer/angle math is common; `svgRef` (for the angle math's center point) and the pointer `handlers` (attached to the big wrapping `div`, not the SVG) are deliberately decoupled. It converts pointer position to "angle from 12 o'clock, clockwise" using the ring SVG's own bounding-box center (compensating for its `-rotate-90` CSS class), then tracks an **unwrapped, accumulating** angle across pointer-move events (via shortest-signed-delta, not the raw `[0, 2π)` value) so multi-lap winding and unwinding both work instead of the angle jumping at the 0/2π seam. `onPointerDown`/`onPointerMove` call `preventDefault()` so the browser's own drag/text-selection gesture never competes with it.

Dragging never changes whether the timer is running — it only ever moves the `elapsed` value. Both files' `recompute()` (the wall-clock tick, see above) no-ops while a drag is in progress via an `isDraggingRef` guard, so the two don't fight over `elapsed`. On every drag update, `baseElapsedRef` is set to the dragged value and, **only if `runStartRef` was already non-null** (i.e. the timer was actively running when the drag started), it's reanchored to `Date.now()`. That single conditional is the entire mechanism: if it was running, the existing tick naturally continues from the dragged value the instant you let go, with no jump; if it was paused, `runStartRef` stays `null` throughout and nothing ticks after release — it just sits at wherever you left it.

## Countdown vs. stopwatch mode

- **Countdown** (`taskType !== "stopwatch"`): counts down from `projectedMinutes`. Ring color: **olive** from 0–74% of target, **amber** from 75–99%, **burgundy** once elapsed ≥ target — at which point the display flips to counting *up* past the target as `+MM:SS`.
- **Stopwatch** (`taskType === "stopwatch"`): no target, always counts up; the ring fills over a 30-minute soft cap and then stays full. Ring is always olive — there's no color-state logic in this mode.

"Done" computes `actualMinutes = max(1, round(elapsed / 60))` from the local wall-clock value and passes it to the parent; "Missed" passes nothing. Neither button makes an API call directly — `TimerScreen` itself is purely presentational and delegates persistence to callbacks from `TasksView`.

**`TaskFormScreen` has no ring, no countdown/stopwatch color states, and no drag gesture** — it's a plain vertical form (one control per `formFields` entry) with the same elapsed-time tracking running silently in the background purely to compute a fallback `actualMinutes`. Its "Save" button requires every field to have a value, then calls `onComplete(formData, actualMinutes)`; "Missed" behaves the same as elsewhere.

## Server-authoritative start time, and a single-active-timer invariant

`TasksView.handleStartTimer` does **not** just open the timer locally. On a fresh start it first `POST`s `{ state: "in_progress" }` to `/api/task-logs`, which stamps `startedAt` server-side, *then* opens `TimerScreen` — so the source of truth for "when did this start" always lives on the server before the UI even appears. If the task already has an `in_progress` log (resuming), no new POST is made; elapsed time is simply recomputed locally from the existing `startedAt`.

The API enforces, server-side, that **at most one log can be `in_progress` at a time per person** (`performedByUserId` — not per company, since different staff can each have their own timer running; see task-lists-api.md) — any start of a timer first auto-**completes** any other dangling `in_progress` log that same person has, crediting it with the elapsed time since its `startedAt` (plus any `pausedSeconds` it had banked), rather than trusting the client to have closed it out. This is a single shared function, `startInProgressLog` in `lib/task-log-actions.ts`, used by the standalone timer (`handleStartTimer` below) and `TaskListSessionView.tsx`'s per-item effect (a session's own task starts) — not duplicated logic, so every entry point behaves identically by construction. A now-deleted API-key-authenticated external endpoint, and later the NFC tap-to-trigger flow, used to be additional callers here (see `docs/project-structure.md`'s note on the former's removal and `docs/features/nfc.md`'s "History: Tap-to-trigger (removed)" for the latter). `handleStartTimer` re-fetches the day's logs after posting so a stray task auto-resolved this way is reflected in the UI too, not just the task that was just started.

**Navigating inside an already-open Task List Session is the one exception** to this sweep-to-complete behavior — see "Single active timer, pause instead of complete or run concurrently" below, where the task being left is *paused*, not completed, via a different function (`switchActiveLog`).

`sessionTaskListId` gets stamped on the log by `TaskListSessionView.tsx`'s own per-item effect whenever a session's task starts (the primary path — see task-lists-api.md's Task Logs section) — that single field is what lets a resume land the user inside a Task List Session instead of the standalone timer, see below. The now-deleted external endpoint used to be able to set it too, via a `routineGroupId` param — the one way to anchor a session for an *anytime* list specifically, since those have no in-app "Start Tasks" button at all; see `docs/features/anytime-tasks.md`'s note on that capability now being gone entirely.

On completion, `TasksView.handleTimerComplete` `PATCH`es `{ state: "done", actualMinutes }` — but the server derives `actualMinutes` itself from `now - startedAt` when a `startedAt` exists (see task-lists-api.md); the client-sent value is only a fallback for the edge case where no `startedAt` is on record.

## Resuming after a reload or app close

Because `startedAt` is already persisted before the timer UI opens, closing the tab/app entirely and reopening it does not lose progress: `TasksView` has a mount-time effect that scans the day's logs for one with `state === "in_progress"` and a `startedAt`, computes elapsed as `Date.now() - startedAt`, and reopens `TimerScreen` automatically with that seeded value — reproducing the exact resume behavior of manually tapping "Resume Timer" on an in-progress row. Since the single-active-timer invariant above guarantees at most one `in_progress` log exists per person at any time, this scan is never ambiguous about which task to reopen.

This shared lookup — `TasksView.openInProgressTimer()` — is also what the FAB's resume tap (`?resumeTimer=1`, see below) and manually tapping "Resume Timer" on a row (`handleStartTimer`'s resume branch) both call, so all three entry points branch the same way: if the in-progress log's `sessionTaskListId` is set, it resolves that list and the task's index within it and opens `TaskListSessionView` there instead — reproducing "tapped Start Tasks and navigated to that task by hand." If the list or task can't be resolved (e.g. the list was deleted since), it falls back to the standalone timer rather than failing silently. With no `sessionTaskListId` (the ordinary case — tapping Start Timer in the app never sets one), it's always the standalone `TimerScreen`, and completing or missing it just closes the timer screen and returns to the plain Tasks home, with nothing else active.

> **Fixed** (commit `f8db478`, 2026-08-29): `openInProgressTimer()` reads `sessionTaskListId` off `initialLogs`, the prop `TasksView` gets from the server. `app/(app)/tasks/page.tsx`'s mapping of `todayLogs` into that prop previously never included `sessionTaskListId` (unlike `serializeLog` in `lib/task-log-actions.ts`, which the client-side `/api/task-logs` fetch used elsewhere goes through and does include it), so a genuine SSR entry to the page — the mount-time auto-resume effect, and the FAB's `?resumeTimer=1` navigation, both of which run before any client fetch happens — always saw a session-anchored `in_progress` log as unanchored and fell through to the standalone `TimerScreen`, even though it should have reopened `TaskListSessionView`. `initialLogs`' mapping now sets `sessionTaskListId: l.sessionTaskListId ? l.sessionTaskListId.toString() : null` (`app/(app)/tasks/page.tsx:140`), so SSR-driven resume paths reopen a session correctly, matching the client-fetch path.

The FAB (`components/BottomNav.tsx`) surfaces whichever timer is active app-wide for the signed-in person, with a live clock, and its resume tap navigates to `/tasks?resumeTimer=1&date=…`, which `TasksView` reads via a dedicated (non-mount-only) effect so it works even if the Tasks page was already mounted.

## The sequential session (`TaskListSessionView.tsx`)

`TaskListSessionView` steps through a list's tasks, but only one task's timer is ever actually running at a time — including across jumps. `startIndex` — which task it opens on — comes from wherever it was opened: manually tapping "Start Tasks" computes the list's first not-yet-`done` task; resuming a `sessionTaskListId`-anchored log (see above) instead lands on whichever specific task the anchor points at, regardless of whether earlier tasks in the list are complete.

### Form tasks inside a session

When the current task is a `form` task, `TaskListSessionView` returns `TaskFormScreen` as a full-screen takeover instead of its own ring markup — same component, same props shape `TasksView`'s standalone path uses (`item`, `initialElapsed`, `onComplete`, `onMissed`, `onClose`). Completing it (`handleTaskFormDone`) calls `advance("done", actualMinutes, formData)` — `advance`/`saveLog` route through `PATCH /api/task-logs` (not the usual `POST`) whenever `formData` is present, so the captured field values persist the same way they would outside a session (see task-lists-api.md's `PATCH /api/task-logs`). Returning to the session view for the next task happens automatically once `advance()` moves `currentIndex` forward, the same as any other completion.

### Which task list is running

`TaskFormScreen`/`TimerScreen` both take an optional `taskListName` prop, rendered as a small uppercase kicker line above the task's icon/name — added since neither screen otherwise said which shift the current task belonged to once you were past the initial "Start Tasks" tap. `TaskListSessionView` passes its own `taskListName` straight through to its embedded `TaskFormScreen`, and also shows the same label in its own ring-phase top bar, between the close button/counter row and the "Projected finish" line. The standalone path (`TasksView.tsx`'s own `TaskFormScreen`/`TimerScreen` renders, used for anytime tasks and any task opened outside a session) passes `findTaskListName(timerItem._id)` — the same lookup already used to label a standalone task's Live Activity — so it works for every entry point, including the FAB scan paths in [nfc.md](nfc.md), without needing its own separate plumbing.

### Single active timer, pause instead of complete or run concurrently

`TaskLog` has a `paused` state (distinct from `in_progress`) and a `pausedSeconds` field banking elapsed time from earlier running segments. Whenever the current task changes — advancing, or tapping a row to jump — an effect keyed on the current index calls `switchActiveLog` (`lib/task-log-actions.ts`, via `POST /api/task-logs` with `sessionNav: true`): whatever was `in_progress` gets flipped to `paused` (elapsed banked, `startedAt` cleared), and the new current task is stamped `in_progress` — resuming from its own banked `pausedSeconds` if it was paused earlier, or starting fresh otherwise. Nothing here ever sets a terminal state (`done`/`missed`) — jumping away from a task never marks it done or missed, only Done/Missed (app button or the external API) does that. This is deliberately different from `startInProgressLog` (used by the standalone timer and the external API), which still auto-*completes* whatever else that same person has `in_progress` — moving your attention to a different task inside an already-open session isn't the same signal as "I've started doing something else in real life."

Checkbox and form tasks are skipped by this in-progress-timer step entirely (no ring timer to track — a form task gets its own elapsed tracking inside `TaskFormScreen` instead, see "Form tasks inside a session" above), but still trigger the same switch-and-pause call so whatever else was running gets paused while you're on them. This per-task call always passes `sessionTaskListId`, so closing the app mid-session (without tapping X) resumes straight back into the session on reopen, not the standalone timer. It's also what opens (or reuses) the list's persisted `TaskListSession` record and counts a jump — see "A persisted session record" below.

Tapping Done/Missed calls `advance()`, which `POST`s a terminal-state log for the current task, then **re-fetches the day's logs from the server** and moves to the next task that isn't `done`/`missed` — `paused` and `in_progress` tasks are deliberately not treated as "handled." That search (`nextUnfinishedIndex`) walks forward from the current index first, then **wraps back to the start of the list** rather than stopping at the end — so an earlier task left `paused` (jumped away from) or never touched (jumped over) still gets revisited instead of the session silently reaching the summary screen while it's still outstanding. The summary phase is only reached once every task in the list is truly finished. The same wrap-around search is used by the foreground-revalidation effect below.

A separate `visibilitychange`/`focus`/`pageshow` effect re-fetches the day's logs and checks whether the current task's log is still `in_progress` or `paused` (i.e. still legitimately "ours" or otherwise unresolved) — if it's now a terminal state instead, something outside this session completed it (an external trigger, another tab/device, or another employee), so the session adopts that real result and advances via the same wrap-around search rather than trusting a stale local clock. The same effect also re-runs on a 2-second `setInterval`, not just those events, so an external trigger (App Intent / Siri / Shortcuts) is caught even if the session stays foregrounded the whole time rather than requiring a background/foreground cycle to notice — no separate SSE/push channel was worth building for this given Vercel's serverless model doesn't reliably share in-memory state across invocations, so polling (gated on `document.visibilityState === "visible"` and `phase === "running"`, same as the event-driven path) is the deliberate mechanism here.

Tapping X to close the session mid-task just dismisses the view — `handleClose` does nothing but call the parent's close handler. The current task's log is already `in_progress` server-side (stamped by the per-task effect above the moment it became current) and is left running untouched, same as backgrounding the app entirely; nothing is flushed to `done`. (An earlier version of this flushed the current task to `done` with the session's locally-tracked elapsed time on close — deliberately changed, since that made X indistinguishable from actually finishing the task, and the Live Activity, once that shipped, gave a better way to keep a task visibly running after dismissing the session view.) Any task left `paused` when you close (this one or an earlier one jumped away from) is not touched either — it stays `paused`/`in_progress`, resumable later by reopening this session, by tapping its row on the main Tasks list (which detects `paused`/`in_progress` and offers "Resume Timer"), or via the FAB's active-timer indicator (`BottomNav.tsx`). Closing via X and reaching the end via "Finish" both then trigger the same parent handler (`TasksView.handleSessionFinish`), which re-fetches the day's logs and calls `router.refresh()` to resync the UI.

### Live projected finish time

While a session is running, a single line under the top bar reads "Projected finish: 7:45 AM" — a live estimate of when the whole list will actually be done, not just the current task's own elapsed/remaining ring next to it. In-session only: not shown on the FAB's active-timer indicator (`BottomNav.tsx`) or on the standalone `TimerScreen`, since both are single-task, not list-level.

The math lives in `lib/projected-finish.ts`, kept separate from the component so it's testable without a rendered session:

- Every task in the list resolves to one of four projection states, computed fresh on every render (including the once-a-second tick that already updates `elapsed`, so this stays live without a second interval): the **current task** is always `active`; everything else is `done`/`missed` if a terminal log exists for it (checked in the same `sessionLogs` → `latestLogs` → `externalLogs` precedence the task list below already uses per row), or `pending` otherwise.
- `done`/`missed` tasks contribute **nothing** to the projection — their time already happened, and that's already reflected in wherever "now" currently sits. Every `pending` task contributes its full `projectedMinutes`.
- **The `active` task is pinned to a fixed clock time — `targetInstant` — for as long as it's still within its own target, and only starts tracking live once it runs over.** `targetInstant` (`TaskListSessionView.tsx`) is computed from the same stable `baseElapsedRef`/`runStartRef` pair the ring's own elapsed display uses — `runStartRef - baseElapsedRef*1000 + projectedMinutes`, i.e. "when this task's clock effectively started" plus its target duration — **not** `Date.now() - elapsed` re-sampled every render. That distinction matters: `elapsed` only updates once a second (the tick), while a fresh `Date.now()` at render time is continuous, so deriving the target instant from those two on every render would only *approximately* cancel against `now` in `remainingMinutes` (see below) — close enough not to visibly drift most of the time, but not a guarantee, and it invites off-by-a-few-hundred-ms rounding right at a minute boundary. Anchoring to a value that's only recomputed when the task's start/pause state actually changes (pause, resume, jump, ring-drag) — never on the tick itself — makes the freeze exact: **if you finish exactly on your projected time, the displayed finish never moves at all; it only changes if you finish early or run over.**
- Concretely, `remainingMinutes` (`lib/projected-finish.ts`) contributes `(targetInstant - now) / 60000` for the active task while `now < targetInstant`, and `0` once `now >= targetInstant` — from that point the projection is just `now + pendingSum`, ticking forward live, one second at a time, for exactly as long as the task runs over.
- The projection is **`now + remainingMinutes`**, anchored to `Date.now()` at render time — deliberately not the list's original `startTime` + total projected duration. This is what makes it live: if the session started late, or an earlier task ran long, that's already baked into where "now" sits (and into `targetInstant`, which is derived from the same real start time); the formula doesn't need to separately reconstruct how the day went to get there. (Summing already-`done` tasks' real `actualMinutes` on top of `now` would double-count time that's already elapsed — a tempting-looking but incorrect reading of "total minutes across every task's real/projected time," since that total needs to be anchored at the list's actual start, not at `now`, to mean anything; anchoring the *remaining-only* total at `now` is the one combination that's both live and correct.)
- Marking a pending or active task Missed doesn't need its own special case: it just stops being `pending`/`active` and starts contributing zero like any other terminal-but-zero state, which is what pulls the projected finish time earlier immediately (the "skip the shower and the leave time pulls earlier" behavior from the original ask).

An optional on-track/behind indicator colors the line (`text-olive-light` ahead of schedule, `text-amber` behind — the same "running over" color the timeline below uses, so both signals read consistently) by comparing the live projection against a static baseline — `startTime + total projectedMinutes` across the list's timed tasks (checkbox tasks excluded, the same convention `TaskListCard.deriveCollapseAfter` already uses for a list's collapse-after time). `TaskListSessionView` receives the list's `startTime` via a `taskListStartTime` prop (`TasksView` passes `sessionTaskList.startTime`); lists without one (custom lists) show the plain projected time with no color verdict, since `staticBaselineFinish` returns `null`.

Nothing here is persisted — it's a pure client-side derived value recomputed from data the session already has loaded (`tasks`, `sessionLogs`, `latestLogs`, `externalLogs`), same as the rest of this component's state.

### Live task list timeline

Directly under the "Projected finish" line, a thin horizontal bar renders one segment per task, left to right in list order, with the list's actual start time on the left and the live projected finish time (same value as the line above) on the right. The math lives in `lib/task-timeline.ts`'s `computeTimeline`, kept separate from the component the same way `lib/projected-finish.ts` is — it consumes the *same* per-task `TaskProjection[]` array the projected-finish line already builds each render (`done`/`missed`/`active`/`pending`, via the same `sessionLogs` → `latestLogs` → `externalLogs` → pending precedence), so the timeline and the finish-time label can never disagree about what state a task is in.

The bar itself (the row of colored segments plus the start/end labels underneath) is a shared presentational component, `components/TimelineBar.tsx` — it just renders whatever `{id, pct, color}[]` segments and labels it's handed, with no notion of live/done/pending state of its own. `TaskListSessionView.tsx` is the one that maps its `TimelineColorState` segments to hex via `TIMELINE_COLOR` before passing them in.

- Each task resolves to a segment width in **minutes**, not a fixed original allocation: `done` contributes its real `actualMinutes` (falling back to `projectedMinutes` if that's somehow missing); `pending` contributes its full `projectedMinutes`; `missed` contributes `0` and is dropped from the bar entirely (`segments` filters out zero-width entries) — the same "terminal-but-zero" treatment `remainingMinutes` in `lib/projected-finish.ts` gives them, so skipping a task shrinks the bar instead of leaving a dead segment in it.
- The **active** task's width is derived from the same `targetInstant` anchor the projected-finish line uses (`elapsed = (nowMs - (targetInstant - projectedMinutes * 60000)) / 60000`), not a separately-tracked elapsed value — one source of truth for "how far into this task are we really," recomputed on every render including the once-a-second tick. Its width is normally exactly its `projectedMinutes` (matching the bar's other segments' "planned" widths) and only grows past that once it runs over — which is what visibly makes the active segment eat into the rest of the bar's share as the minutes tick by, rather than the bar just growing off the end.
- Segment widths are proportional shares (`pct = minutes / totalMinutes * 100`) of the list's **current** running total, not the original static plan — so the bar continuously re-proportions itself as tasks finish, run long, or get skipped, instead of showing a fixed layout computed once at session start.
- **Color** (`TimelineColorState`, mapped to hex in `TaskListSessionView.tsx`'s `TIMELINE_COLOR`): `done` and on-track `active` both render **olive** (the same "success/in-hand" convention `TaskRow`'s done badge uses, regardless of variance) — only a running-over active segment shifts to **amber**, matching the on-track/behind indicator's own amber, so both signals read as one consistent "running behind" color rather than two. `pending` segments render as a dim neutral fill (`border-light`) — not yet decided, not a verdict.
- `startInstant` (the bar's left-edge label) is reconstructed as `now - (doneMinutes + activeElapsedMinutes) * 60000` — the real wall-clock instant implied by every task that's actually happened so far, deliberately excluding pending tasks' projected time (hasn't happened yet) and any paused/idle time in between (the same simplification `TaskListSessionView`'s own `totalActualMinutes` already makes for the summary screen — see "A persisted session record" below). It is **not** the list's `startTime` setting; a session that started late or ran with gaps shows that honestly rather than pretending it began on schedule.
- Segment borders use a 2px background-colored gap (not a visible border color) between segments, purely so adjacent same-color segments (e.g. two `done` tasks in a row) still read as distinct pieces of the bar.

### A persisted session record

`TaskListSessionView.tsx`'s own rendering still reconstructs "today's session" on every read by joining `TaskLog` rows on `sessionTaskListId` + date (`fetchDayLogs()`) — that part is unchanged. Alongside it, a real `TaskListSession` document (`models/TaskListSession.ts`, `tasklistsessions` collection — see [task-lists-api.md](../api/task-lists-api.md#task-list-sessions)) is now created and maintained as a side effect of the same write paths, giving "when did I actually start/finish this task list" a durable answer instead of one reconstructed from log timestamps every time:

- **Created** the moment the list's first task actually starts running — `startInProgressLog` and `switchActiveLog` both call `ensureOpenSession` whenever they're given a `sessionTaskListId`, reusing any already-open session for that list/date rather than creating a second one.
- **Updated** every time a task tied to an open session reaches `done`/`missed` — `completeInProgressLog`, `startImmediateLog`, and both `POST`/`PATCH /api/task-logs`'s terminal branches all call `recordSessionCompletion`, which appends to `completionSequence`, folds `actualMinutes` into `totalActualMinutes` for `done` (zero for `missed`, same as the live-projection math above), and closes the session (`status: "completed"`, `completedAt: now`) the moment every active task in the list has a terminal log.
- **`pauseOrJumpCount`** increments whenever `switchActiveLog` actually pauses another task (not on the session's opening move, which has nothing to switch away from). (The now-removed NFC tap-to-trigger flow's own jump case used to increment this too — see `docs/features/nfc.md`'s "History: Tap-to-trigger (removed)".)

This is purely additive — nothing about the in-app rendering above changed, and there's no read endpoint for these records yet. See [task-lists-api.md](../api/task-lists-api.md#task-list-sessions) for the full shape and a known gap around checkbox/form-task-first lists triggered externally.

- `components/TaskFormScreen.tsx` — the primary single-task full-screen UI today; field-based, no ring.
